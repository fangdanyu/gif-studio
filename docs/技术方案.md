# GIF Studio 技术方案与需求对照

> 依据：桌面《GIF编辑器小程序开发需求文档》（2026-03-25，微信小程序方案）
> 本次交付：**原生 Android 应用**（按你的要求把产品形态从微信小程序改为安卓 App）

---

## 一、方案调整说明

需求文档按微信小程序设计，技术栈是 `gif.js + Canvas + ffmpeg.wasm`。改为原生 Android 后，
有几处必须替换，理由如下：

| 需求文档中的选型 | 小程序阶段的问题 | 本项目采用的方案 |
|---|---|---|
| gif.js / libgif-js 编码 | JS 编码在低端机慢，且依赖 Canvas 读像素，易 OOM | **自研 Kotlin GIF89a 编码器**（中位切分量化 + LZW），纯 CPU，无 WebView 开销 |
| ffmpeg.wasm 视频转 GIF | wasm 包体积大、内存占用高，小程序包体也放不下 | **MediaMetadataRetriever 逐帧抽帧**，按指定 fps 采样，零额外依赖 |
| Canvas API 做裁剪/滤镜 | 需要把每帧转成 ImageBitmap，内存翻倍 | **Bitmap + Canvas + ColorMatrix 渲染管线**，预览和导出共用同一套绘制代码 |
| 微信云开发存素材 | 需要账号与云环境 | 内置 24 款贴纸 + 6 款模板，全部离线；`Pictures/GifStudio` 存作品 |
| 微信分享 / 复制链接 | 小程序内分享 | 系统分享面板（微信、QQ、相册等均可），无「复制链接」 |
| 小程序录屏转 GIF | 平台限制，本就不易实现 | 改为「拍摄转 GIF」，调系统相机录制后直接导入 |

此外，需求文档里「无水印导出」是核心痛点，本项目所有导出一律无水印，且不设付费墙——
第 6 章商业模式建议在本版本中未落地（见第九节后续规划）。

## 二、总体架构

```
┌───────────────────────────── UI 层 ─────────────────────────────┐
│ MainActivity（首页/视频·图片·拍摄入口）                          │
│ EditorActivity（预览 + 帧条 + 工具条 + 导出）                     │
│ GalleryActivity（我的作品）  TemplateActivity（表情包模板）        │
│ GifPreviewView（自绘预览：帧动画 + 图层绘制 + 拖拽命中测试）        │
└───────────────┬─────────────────────────────────────────────────┘
                │ 读取同一个 GifProject
┌───────────────▼──────────── 领域层 ─────────────────────────────┐
│ model/GifProject        原始帧 + 延时 + 裁剪 + 速度 + 倒放 + 图层  │
│ edit/ProjectRenderer    非破坏渲染：裁剪→缩放→滤镜→涂鸦/文字/贴纸   │
│ media/ExportEngine      质量分档、抽帧、调色数、进度回调            │
└───────────────┬─────────────────────────────────────────────────┘
                │
┌───────────────▼──────────── 编解码层（纯 JVM，可单测）────────────┐
│ gif/GifQuantizer   15bit 直方图 + 中位切分 + 颜色缓存映射           │
│ gif/GifEncoder     GIF89a：GCE/局部色表/LZW/循环/1bit 透明          │
│ gif/GifDecoder     LZW 反解/隔行/处置方式/透明/降采样解码           │
└─────────────────────────────────────────────────────────────────┘
```

关键设计：**原始帧只读，所有编辑都在渲染阶段生效**。这样撤销、改参数都不需要重算帧，
预览（小尺寸）与导出（全尺寸）共用 `ProjectRenderer` 的绘制逻辑，所见即所得。

## 三、GIF 编码实现

`GifEncoder.encode(width, height, frames, delaysCentis, loopCount, maxColors)`

每帧流程：

1. **颜色量化**（`GifQuantizer`）
   - 把像素按 R/G/B 各 5bit 落到 32768 个桶做直方图，累计每桶计数与 RGB 和；
   - 有效桶作为「中位切分」样本，按「最长通道 × 像素数」挑选待切分盒，
     沿最长通道排序后按像素数中位切开，直到盒数达到目标色数（≤256）；
   - 每个盒取加权平均色作为调色板项；
   - 像素映射用 15bit → 索引的缓存表，命中 O(1)，未命中才做 256 次最近色搜索，
     避免 40 万像素 × 256 色的暴力扫描。
2. **透明处理**：只要该帧存在 alpha<128 的像素，就预留一个调色板索引作为透明色，
   写 GCE 时置透明标志并把处置方式设为 2（恢复背景），保证解码端不会残留上一帧。
3. **LZW 编码**：标准 GIF 变长码（9→12bit），码表满 4096 时发清除码重建；
   位流 LSB 优先打包，按 255 字节切子块写出。
4. **文件结构**：`GIF89a` 头 + 逻辑屏幕描述 + `NETSCAPE2.0` 循环扩展 +
   逐帧 `GCE / 图像描述符 / 局部色表 / LZW 数据` + 尾字节 `0x3B`。
   每帧用局部色表，不同帧各自 256 色，避免多色画面共用一张表导致偏色。

## 四、GIF 解码实现

`GifDecoder.decode(bytes, scale, maxFrames, maxTotalPixels)`

- 完整解析 87a/89a：全局/局部色表、GCE（延时/透明/处置方式）、应用扩展（循环次数）、
  图像描述符（位置、尺寸、隔行标志）；
- LZW 反解支持 KwKwK 特例与码表重建；隔行图按 4 遍（0/4/2/1 起始）还原行序；
- 处置方式 0/1 保持画布、2 清空帧区域、3 恢复上一帧（备份画布）；
- **降采样解码**：按 `scale`（1/2/4/8）把像素写到缩小后的画布，配合 `maxTotalPixels`
  预算，1080p 长 GIF 也不会一次吃掉几百 MB；
- 输出 `ARGB` 帧数组，透明像素 alpha=0，供上层转 Bitmap 后继续编辑。

## 五、编辑能力实现

| 能力 | 实现方式 |
|---|---|
| 裁剪 | 归一化裁剪矩形（0~1）；预览进入 `MODE_CROP` 后在画面上**拖拽框选**（四角手柄缩放 / 框内平移 / 框外重画），应用时叠加到已有 crop：`newL = cropLeft + rectL·(cropRight-cropLeft)`，故可反复精修；渲染时做 `drawBitmap(srcRect→dstRect)` |
| 裁剪固定比例 | 工具条「自由 / 1:1 / 3:4 / 4:3 / 16:9 / 9:16」；`setCropAspect(ratioWH)` 把目标比例换算为归一化比例（`ratioWH / 画面宽高比`）后 `fitCropToAspect()` 居中放最大框；`setRectByCorner()` 在锁定比例时「宽主导、高不足改高主导」补齐并 clamp（0~1，最小边 0.06），因此拖任意角都只能按比例伸缩 |
| 裁剪控点 | `cornerPoints()` 由真实四角沿对角线内缩 `1.6 × 8dp`，绘制与命中判定用同一组点，命中阈值 `touchSlop × 1.9`，避免控点贴边难点 |
| 尺寸 | 自定义输出宽度，高度按裁剪后比例换算；`outputSize()` 同时服务预览与导出 |
| 速度 | 不改帧，只改每帧显示延时 `delay/speed`，预览动画与导出延时同步生效 |
| 倒放 | 逻辑帧号 → 源帧号 的反向映射，延时同步反向 |
| 滤镜 | `ColorMatrix` 9 组预设，作为 `Paint.colorFilter` 叠加在绘制阶段 |
| 文字 | 归一化中心点 + 字号比例 + 旋转角，三种样式（描边/纯色/底色块），拖动移动 + 右下角圆点手柄拖动缩放（`sizeRatio` 0.04~0.95）+ **双指捏合缩放与旋转** |
| 贴纸 | 24 款 emoji 贴纸，归一化坐标 + 尺寸比例 + 旋转角，支持拖动、缩放手柄、双指捏合旋转 |
| 图片贴纸 | `ImageOverlay(bitmap, cx, cy, sizeRatio, rotation)`，`sizeRatio` 是**高度占画面比例**，宽度按 `bitmap.width/height` 自动；贴纸弹窗顶部「＋ 从相册添加图片」→ `PickVisualMedia` → `MediaLoader.loadBitmap(480)`，放置时按长边比例（0.12~0.6）并即时选中；渲染顺序为 涂鸦 → 图片贴纸 → 表情贴纸 → 文字 |
| 双指变换 | `ACTION_POINTER_DOWN` 记录双指间距/角度/中点与该图层初始 `sizeRatio`/`rotation`；`ACTION_MOVE` 按间距比缩放（0.15~6 倍，结果再钳 0.04~0.95）、角度差旋转、双指中点位移平移；`ACTION_POINTER_UP`/`UP` 收尾并回调 `onOverlayMoved`。三类图层（文字 / 表情 / 图片）统一 kind，命中测试把触点反向旋转到图层本地坐标，选择框按中心+半宽高+旋转绘制 |
| 涂鸦 | `DoodleStroke(points 归一化坐标序列, color, widthRatio 相对画高)`；`MODE_DOODLE` 下按下起笔、移动累积、松手落库，`ProjectRenderer.drawDoodles` 以 ROUND 线帽 Path 绘制在贴纸/文字之下；支持撤销一笔与清空 |
| 帧管理 | 长按帧条进入多选，点选切换；`removeFrames()` 用逻辑→源帧索引映射后降序删除，并强制至少保留 1 帧 |
| 帧时长 | 统一设置每帧停留时间 50~1000ms；多图合成不再弹帧率选择框，固定 200ms/帧进入编辑（可在编辑页用「速度」调整） |
| 图层提示 | `onOverlaySelected` 首次触发时弹一次 toast（按图层类型区分文案），避免每次选中都打断 |
| 退出保护 | `confirmExit()` 统一接管顶栏返回箭头与系统 BACK：未导出时弹「还没有导出」，给「导出 / 放弃修改 / 继续编辑」；`exportedOnce` 在导出成功后置真，之后退出不再提示 |

导出分三档（`ExportEngine.Quality`），另加「按目标体积自适应」：

| 档位 | 长边 | 调色板 | 抽帧 |
|---|---|---|---|
| 高清 | ≤720 | 256 色 | 全帧（超过 40 帧仍会抽帧） |
| 标准 | ≤480 | 128 色 | 全帧 |
| 压缩 | ≤320 | 64 色 | 每 2 帧取 1，最多 40 帧 |
| 按大小 | 12 档梯度：720/256/1 → 180/24/5 | 逐档下降 | 逐档加大步长 |

抽帧时把被丢弃帧的延时累加给保留帧，保证总时长不变。

**按体积导出**（`exportWithinSize(targetBytes)`）：从最高质量档开始编码，一旦结果 ≤ 目标体积立即返回；
全部档位都超标则返回最小的那一档，并在结果弹窗展示真实体积，不做虚假承诺。进度条按「档位 × 档内进度」加权显示。

**循环次数**：导出弹窗提供「无限 / 1~5 次」6 个选项，值透传到 `GifEncoder.encode(loopCount)`，
写入 NETSCAPE2.0 循环扩展（0 表示无限）；`loopCount` 同时保存在 `GifProject`，`updateInfo()` 实时显示当前设置。

**导出体积预估**：弹窗打开后按当前画质真编码一次，把字节缓存在 `estimateBytes[画质]`，界面上以
「「高清」档约 30 KB」形式提示；切画质或切循环都重新计算，点「导出」时优先复用缓存字节（命中缓存则不做第二次编码），
任何编辑动作（`afterVisualChange()`）会清空缓存，避免显示过期的体积。


## 六、内存与性能策略

| 环节 | 限制 |
|---|---|
| 图片导入 | 长边 ≤720，先按 2 的幂采样解码，再精确缩放；读取 EXIF 方向自动转正 |
| 视频抽帧 | 每帧 320/480/640 宽可选，最多 40 帧 |
| GIF 导入 | 最多 64 帧，总像素预算 2600 万，按倍数降采样解码 |
| 合成图片数 | ≤30 张 |
| 预览渲染 | 长边 ≤420，切滤镜/裁剪时重建，旧帧立即 `recycle()` |
| 编码 | 逐帧渲染→取像素→立即释放位图，峰值只有「一帧全尺寸位图 + 调色板」 |

## 七、与需求文档的性能指标对照

需求文档要求（小程序场景）：30 帧内生成 <5s、最多 100 帧、输出 <10MB、首屏 <2s、内存 <300MB。

本项目实测数据见 `docs/测试记录.md`，其中编码速度在中端手机上按「480 长边 / 30 帧 / 256 色」
基准测试（同一份 Kotlin 代码在 JVM 上测得，手机 CPU 与桌面同数量级，通常慢 2~3 倍）。

## 八、界面实现

- 主色：活力橙 `#FF6B3D` → 玫红 `#FF4E6B` 渐变，辅以紫色 `#7C4DFF` / 青色渐变卡片；
- 应用图标：渐变底（`#FF7A18 → #FF3D77 → #7B2FF7`，vector `aapt:attr` 线性渐变）+ 白色 "GIF / Studio" 文字，
  自适应图标 `mipmap-anydpi-v26` + 108dp PNG 前景（各密度由 `tools/make_icon.py` 生成），
  同时保留传统 `mipmap-*/ic_launcher.png` 供 API 26 以下使用；
- 首页：渐变功能卡 + 双列快捷入口（「我的作品」只保留这一处入口，底部作品区已删除）；最底部居中页脚
  「产品设计：FDY　版本：1.1.0」，版本号从 `PackageManager.getPackageInfo` 读取（失败回退写死值），11.5sp 灰字；
- 编辑页：深色沉浸式背景，预览区（棋盘格提示透明）→ 帧条（横向缩略图，多选态带描边与降透明）→ 工具条（横向滚动、按模式切换）→ 输出信息（含循环次数）；
  裁剪模式工具条顺序为「应用裁剪 / 重置选框 / 取消 / 自由 / 1:1 / 3:4 / 4:3 / 16:9 / 9:16」，当前比例 chip 高亮；
- 交互：文字/贴纸/图片贴纸添加后直接手指拖动，选中图层出现旋转虚线框与右下角缩放手柄，双指可捏合缩放与旋转；裁剪为拖框交互（控点内缩）；所有弹窗均为 Material 风格。

## 十、已知限制

1. 视频抽帧依赖系统解码能力，极端格式（如 HEVC 10bit、部分封装）可能抽不到帧，表现为「生成失败」提示。
2. GIF 解码对少数非标准文件（超长色表、损坏 LZW）容错有限，会提示「无法解析」。
3. 「拍摄转 GIF」调用系统相机，录制质量与时长上限由相机应用决定（已设置 15 秒上限）。
4. 未做横屏/平板适配，页面固定竖屏。
5. 涂鸦笔迹作用于所有帧（同一笔画在每帧出现），未做「仅标注当前帧」的分帧涂鸦；
   如需扩展，给 `DoodleStroke` 增加 `frameIndex` 并按帧过滤即可。
6. 按体积导出的 12 档梯度是经验参数：极小目标（如 0.5MB）配大量帧时，可能停在最后一档仍略超目标，
   此时结果弹窗展示真实体积，不谎报达标。
7. 图片贴纸的 `Bitmap` 未在删除图层时立即 `recycle()`：单张限长边 480、数量少，退出编辑随项目统一释放。
8. 文字旋转后命中检测使用未旋转包围盒近似，包围盒略大于文字实际范围，极端角度下点击空白处也可能选中文字。
9. 固定比例裁剪切换比例后选框重新居中取最大框，不保留上一比例的位移，需要再拖角微调。
10. 双指手势无法在 headless 模拟器上用 adb 复现（`input` 只支持单点、无 root 无法 `sendevent`），
    改用设备内 instrumentation 测试（`PinchGestureTest`）投递真实双指 MotionEvent 覆盖应用层逻辑；
    真机手感仍需实机人工确认。
